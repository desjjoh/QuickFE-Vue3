# Session regression scenarios

[Testing](testing.md) · [Architecture](architecture.md)

These checks exercise the real frontend stores, interceptor, forms and router against controlled responses. Browser scenarios run against production output and use actual tabs, Web Locks, BroadcastChannel and localStorage. HTTP and account fixtures are mocked; these results are not live QuickAPI authentication verification.

| Scenario                                    | Evidence and assertions                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Delayed sign-in/sign-out                    | `test/unit/app/hooks/actions.spec.ts` and `test/e2e/auth-workflows.spec.ts`: late success/failure cannot replace a newer account, purge a newer session, close its dialog or display obsolete errors.                                                                                                                                        |
| Canceled MFA/registration                   | Action tests cover cancellation during CSRF waits, verification and resends. Browser tests cancel pending verification, reopen sign-in, and preserve the new draft after success or failure arrives.                                                                                                                                         |
| Account replacement during refresh          | Auth lifecycle, real interceptor/store integration and browser tests preserve the new account and reject old credentials. A pending destination may load afresh for the replacement account.                                                                                                                                                 |
| Same-account re-login                       | A new login rotates session identity; old actions and refreshes are canceled despite an unchanged user ID. Ordinary token refresh preserves identity.                                                                                                                                                                                        |
| Overlapping generations                     | Lifecycle tests complete the oldest refresh after a newer refresh finishes and a third starts; old cleanup cannot delete the current promise or lock.                                                                                                                                                                                        |
| Concurrent/staggered unauthorized responses | `test/unit/shared/stores/auth-recovery.spec.ts` exercises the real interceptor and store together: one refresh, unchanged request payload/version/idempotency key, reuse of already-rotated valid tokens and a single replay limit.                                                                                                          |
| Lost refreshing tab                         | Fake-clock tests verify timeout/listener cleanup and retry. A browser test closes the lock-owning tab, verifies that the other tab remains signed in, and recovers through the existing Reload action after the lock expires.                                                                                                                |
| Backend refresh rejection                   | An HTTP 401 from refresh clears authentication and saved expiry. NestJS CSRF rejection (403) renews CSRF and retries refresh once; persistent 403, rate limits, network and server failures retain recovery metadata and release the lock without claiming authentication succeeded.                                                         |
| Sign-in persistence                         | `test/e2e/auth-persistence.spec.ts` signs in without seeding storage, reloads, then opens another tab. It covers successful recovery and one CSRF rejection and retry. Unit tests additionally verify startup recovery after an offline request without reseeding persistence. HTTP responses are controlled, not live account verification. |
| Storage failures                            | `test/e2e/reliability.spec.ts` and storage/preference/auth unit tests cover corrupt JSON, unsupported values, denied getters/operations and exhausted quota. Current-tab authentication remains usable; shared coordination requires working shared storage.                                                                                 |
| Duplicate submissions and transitions       | Action tests suppress duplicate API calls and prevent old close transitions, resends or completion callbacks from manipulating replacement workflows.                                                                                                                                                                                        |

Use `npm run test:coverage` for isolated tests and the coverage gate. Build with `npm run build-only`, then run `node node_modules/@playwright/test/cli.js test --project=chromium`. The browser fixture data and runtime requirements are documented in [Testing](testing.md).

Simultaneous-reload coverage forces stale localStorage mutex reads while a controlled server rejects overlapping rotations with the NestJS 401 message. The browser test verifies Web Locks queue the second tab and both tabs recover. This proves frontend coordination against a simulated rotation contract, not live account integration.

Storage-only account-following coverage signs out in one tab, signs into a different account, and verifies the untouched tab clears the old account and displays the new one without navigation or reload. Browser checks exercise both available and absent BroadcastChannel support; unit tests cover early credential broadcasts, storage clearing, failed recovery, wrong-account responses, stale completion, and listener disposal.

The protected-profile regression opens two guest profile tabs, signs in once, holds both activity requests until they overlap, and validates CSRF headers against a server model that replaces its cookie on every CSRF issuance. Both requests must return 200 with exactly one CSRF issuance and zero refresh calls. New-tab recovery separately asserts that an available peer supplies existing access and CSRF tokens without another backend token request.

## Live local verification

On 2026-10-19, manual checks in the signed-in in-app Chromium browser against the running local NestJS backend retained authentication across a single reload, opening a second tab, and simultaneous reloads of both tabs. No API mocking was used for these checks. This is local smoke evidence, not automated authenticated integration coverage or Firefox verification.

## Remaining integration boundaries

- Adversarial ordering of delayed Set-Cookie responses still needs disposable QuickAPI accounts. Ignoring stale JavaScript responses cannot undo a cookie already applied by the browser.
- Server session expiry/revocation, MFA/email delivery, and production CORS/CSRF/TLS topology still require authenticated backend integration.
- Closing a refreshing browser tab is covered; operating-system sleep, suspended background tabs and clock changes remain separate scenarios.
- Cross-tab coordination requires functioning shared storage and compatible loaded application versions. Web Locks provide atomic exclusion; storage events let account changes propagate without BroadcastChannel. Waiting on legacy storage-only refresh locks still requires BroadcastChannel. Blocked-storage tests prove per-tab recovery rather than coordination without shared persistence.
